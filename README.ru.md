# BlankTrail Proxy — демо прохождения защиты от ботов

**Демо**, наглядно и воспроизводимо отвечающее на один вопрос: голый
Python-**клиент** не проходит через сайт, защищённый Cloudflare или AWS WAF,
а [BlankTrail Proxy](https://blanktrail.com) — проходит.

**English version: [README.md](README.md)**

> ⚠️ **Нужен уже запущенный экземпляр BlankTrail Proxy — этот репозиторий не
> включает его в себя, не устанавливает и не запускает.** Направьте демо на
> порт, который вы уже открыли в BlankTrail, либо на его REST API — тогда
> демо само откроет и закроет порт за вас; в любом случае сам BlankTrail
> должен быть где-то уже запущен.

![Форма настройки демо, заполненная синтетическими значениями: три зарезервированных по RFC 2606 домена в качестве целей, вышестоящий прокси базовой линии на документационном адресе по RFC 5737, линия BlankTrail в режиме REST API с плейсхолдером вместо API-ключа, и блок Transport and TLS.](assets/screenshots/setup.png)

---

## 📚 Возможности

- Запускает **базовую линию** и **линию BlankTrail** на одном и том же
  списке целей и превращает пару результатов в один из четырёх вердиктов —
  PASS, FAIL, VOID или ERROR.
- У базовой линии три режима: через вышестоящий прокси, напрямую или
  отключена.
- Подключается к BlankTrail Proxy либо через уже открытые вами
  преднастроенные порты, либо через его REST API, который сам открывает и
  закрывает порт на время прогона.
- Проверка TLS-сертификата на линии BlankTrail включена по умолчанию и
  поддерживает три источника доверия: хранилище ОС, CA, полученный через
  API, или локальный файл CA.
- Транслирует результаты в реальном времени: бейдж вердикта и
  разворачиваемый необработанный дамп по каждой линии для каждой цели, плюс
  счётчик по ходу прогона.

---

## 📋 Требования

- Python 3.10 или новее.
- Работающий инстанс BlankTrail Proxy — либо один или несколько уже открытых
  в нём портов, либо доступный REST API. Сам BlankTrail в это демо не
  входит.
- Свои цели — демо не поставляется ни с одной и не предлагает их.

## 🚀 Быстрый старт

**1. Установите и запустите.**

| Способ | Как получить |
|---|---|
| Windows, без установки | Скачайте [`blanktrail-demo.exe`](https://github.com/BlankTrail/blanktrail-demo/releases/latest/download/blanktrail-demo.exe) и запустите двойным щелчком |
| Любая платформа, из исходников | `run.bat` (Windows) / `./run.sh` (Linux, macOS) / `python -m blanktrail_demo` (если venv уже готов) |

Exe-файл содержит только само демо — **работающий экземпляр BlankTrail
Proxy всё равно нужен**, точно так же, как и при запуске из исходников (см.
предупреждение выше). Открывается консольное окно с тем же адресным
баннером, что и ниже, и вкладка браузера; Windows может пометить
неподписанный exe-файл как небезопасный — в диалоге SmartScreen в этом
случае нажмите **«Дополнительные сведения» -> «Выполнить в любом случае»**.

`run.bat` и `run.sh` при первом запуске создают локальный `.venv`, ставят в
него зависимости из `requirements.txt` и запускают демо. Чтобы сделать то же
самое руками:

```bash
python -m venv .venv
source .venv/bin/activate      # на Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m blanktrail_demo
```

**2. Откройте страницу.** Процесс печатает адрес и сам открывает его в
браузере:

```
BlankTrail demo -> http://127.0.0.1:8790/
```

Чтобы изменить порт, адрес или отключить автоматическое открытие браузера,
см. «Командная строка» ниже.

**3. Настройте прогон.** Вставьте цели в поле **Targets**, по одному URL на
строку (`#` начинает комментарий; пустые строки игнорируются; до 200 целей
за прогон), настройте базовую линию и линию BlankTrail — см. «Две линии» и
«Два способа подключиться к BlankTrail» ниже — и нажмите **Run**.

**4. Прочитайте результаты.** Результаты приходят потоком в реальном
времени: бейдж вердикта и разворачиваемый необработанный дамп по каждой
линии для каждой цели — см. «Вердикты» ниже.

## ⚖️ Две линии

Каждая цель запрашивается дважды: один раз **базовой линией** (голый клиент
`requests`/`httpx`, без какого-либо участия BlankTrail) и один раз **линией
BlankTrail** (тот же клиент, но через порт BlankTrail). У базовой линии три
режима:

| Режим | Что происходит | Когда использовать |
|---|---|---|
| `upstream` (по умолчанию) | Запрос базовой линии идёт через вышестоящий прокси, который вы указываете | Когда сравнение ниже должно реально что-то значить (рекомендуется) |
| `direct` | Запрос базовой линии уходит напрямую с этой машины | Для быстрой проверки «на дым» — см. предупреждение ниже |
| `off` | Базовая линия вообще не запускается | Когда вы уже знаете, что цель проверяет голых клиентов, и хотите проверить только BlankTrail |

**Направьте базовую линию через тот же вышестоящий прокси, что и порт
BlankTrail.** Линии сравнимы, только если обе выходят с одного и того же
исходящего IP-адреса — тогда единственная разница между ними —
TLS/HTTP2-отпечаток и solver, а это и есть предмет измерения. Запустите
базовую линию в режиме `direct` — и это перестаёт быть правдой: она выходит
с другого IP, чем линия BlankTrail, и тогда PASS или FAIL может на самом
деле объясняться репутацией именно этого IP, а не тем, что сделал
BlankTrail. Демо не скрывает это — режимы `direct` и `off` оба выводят
предупреждение в шапке прогона именно по этой причине.

## 🔌 Два способа подключиться к BlankTrail: готовый прокси-порт или REST API

Линии BlankTrail нужен URL прокси для каждой цели. Демо получает его одним
из двух способов.

**Готовый прокси-порт** — один или несколько портов, уже открытых вами в
BlankTrail, вставленные как есть:

```
http://127.0.0.1:9000
http://127.0.0.1:9001
```

Одна строка — это фиксированный порт, используемый для всех целей; несколько
строк — это пул, который перебирается по кругу (round-robin) по индексу
цели. Демо только читает эти порты и никогда само их не открывает и не
закрывает — ими управляете вы.

**REST API** — демо открывает один порт на весь прогон и закрывает его по
завершении:

```
API base URL: http://127.0.0.1:8891
Порт: 9000        Протокол: HTTP CONNECT
```

По порядку:

1. `GET /api/v1/health` — проверяется заранее, до первого запроса к цели,
   чтобы неверный базовый URL API или ключ провалился один раз и сразу, а не
   по разу на каждую цель.
2. `POST /api/v1/ports/open` — открывает порт с настройками из формы
   (протокол, режим профиля, фильтры браузера/ОС, вышестоящий прокси и
   переключатели, включая **Challenge Breaker (`js_solver`)**, спуфинг
   HTTP/2, авто-ротацию профиля и сохранение сессий).
3. Каждая цель после этого запрашивается через `http://127.0.0.1:<порт>`
   (или `socks5h://127.0.0.1:<порт>` для порта SOCKS5).
4. `POST /api/v1/ports/close` — закрывает порт в конце прогона, если не
   снята галочка **Close the port when done**. Закрытие не гарантировано:
   если оно не удастся, это никак не повлияет на уже полученные вердикты, а
   порт всё равно закроется сам по истечении времени бездействия.

Введённый вами API-ключ отправляется только на настроенный вами базовый URL
API, в заголовке `X-API-Key`, и хранится только в памяти на время прогона —
никогда не записывается на диск и не попадает ни в один лог, ни в одно
событие.

---

## 🖥 Командная строка

```
python -m blanktrail_demo [--port N] [--host ADDR] [--no-open]
```

| Флаг | По умолчанию | Значение |
|---|---|---|
| `--port N` | `8790` | порт веб-интерфейса — собственный интерфейс демо, а не порт BlankTrail |
| `--host ADDR` | `127.0.0.1` | адрес, на котором слушает веб-интерфейс |
| `--no-open` | выкл. | не открывать окно браузера автоматически |

Веб-интерфейс слушает только `127.0.0.1` — доступен с этой машины, но не из
сети, — и не имеет собственной авторизации. Меняйте `--host` только если
понимаете, что именно открываете наружу.

## 🏗 Сборка из исходников

Пользователи Windows могут собрать собственный однофайловый
`blanktrail-demo.exe`, вместо того чтобы скачивать релизную сборку:

```powershell
.\build-windows.ps1
```

Скрипт ставит [PyInstaller](https://pyinstaller.org) в `.venv` (создавая
его, если `run.bat` ещё этого не сделал), собирает демо вместе со всеми
зависимостями времени выполнения в один файл и печатает путь, куда он его
записал — `dist\blanktrail-demo.exe`. PyInstaller нужен только на этапе
сборки: он указан в `requirements-build.txt` и никогда — в
`requirements.txt`, который остаётся списком того, что демо требует во
время выполнения.

## 🔐 TLS и MITM-сертификат

Проверка сертификата на линии BlankTrail **включена по умолчанию**, и это
часть измерения, а не формальность: успешное TLS-рукопожатие доказывает, что
цепочка подменённого сертификата выстроена корректно, а его SAN совпадает с
запрошенным хостом. PASS, полученный при отключённой проверке, на самом деле
этого бы не доказывал. (Базовая линия никогда не идёт через прокси
BlankTrail, так что всё это её не касается — она всегда проверяет
сертификаты как обычный HTTPS-клиент.)

**Ловушка, ради которой всё это написано.** Собственный модуль `ssl` в
Python прекрасно читает хранилище доверенных сертификатов операционной
системы — но `requests` и `httpx` сами по себе им не пользуются. По
умолчанию оба при построении SSL-контекста передают `cafile=certifi.where()`
— путь к бандлу, который `certifi` носит внутри себя, а не к корням вашей
ОС. Это не предположение, а измеренный факт: в Windows 10 / CPython 3.13.5
`ssl.create_default_context()` находит 228 системных корневых сертификатов —
среди них и установленный CA BlankTrail, — тогда как собственный бандл
`requests` указывает на файл, упакованный вместе с `certifi`, а не на
хранилище ОС. Поэтому установка CA BlankTrail в систему ничего не меняет для
обычного вызова `requests.get()` или `httpx.get()`: корневой сертификат,
которому доверяет ОС, лежит рядом, но ни один из клиентов туда не смотрит.
Единственное решение — самим построить SSL-контекст и явно передать его
клиенту; именно это демо и делает для линии BlankTrail.

Три источника доверия, переключаемые радиокнопкой в блоке **Transport and
TLS**:

| Источник | Как строится контекст | Когда нужен |
|---|---|---|
| **OS trust store** (по умолчанию) | `truststore`, если он установлен (читает хранилище ОС через нативный API), иначе собственный `ssl.create_default_context()` из Python | CA BlankTrail уже установлен в систему — обычный случай |
| **Fetch CA from the API** | `GET /api/v1/ca`, объединяется с собственным бандлом `certifi` в один файл на время прогона | Установить CA неудобно или невозможно: контейнер, CI, ноутбук без прав администратора, удалённый инстанс |
| **CA file** | Локальный файл `ca.crt`, который вы указываете, объединяется с бандлом `certifi` тем же способом | CA уже есть в виде файла, и устанавливать его в систему не хочется |

Два последних источника строят **объединённый** бандл — корни `certifi`
плюс CA BlankTrail, — а не замену. Цель, исключённая из MITM-порта,
предъявляет собственный настоящий сертификат, и бандл, содержащий только
корень BlankTrail, не смог бы её проверить. Если выбранный источник не
срабатывает (файл не найден, запрос к API не удался), прогон отказывается
стартовать — вместо того чтобы молча откатиться к отсутствию проверки:
зелёный вердикт не должен получаться на прогоне, где проверять было нечем.
Отдельная галочка **Disable TLS verification** существует для диагностики,
по умолчанию она снята, и её включение означает, что полученные вердикты
больше не доказывают корректность цепочки сертификата.

**Отдельно про macOS.** В Windows и Linux собственный контекст Python из
стандартной библиотеки и так читает хранилище ОС, поэтому источник «OS trust
store» работает даже без установленного `truststore`. На macOS это не так:
CPython сам по себе не читает Keychain, и установленный туда CA для голого
`ssl.create_default_context()` попросту невидим. Пакет `truststore` (указан
в `requirements.txt` и ставится автоматически скриптами запуска) закрывает
этот пробел, обращаясь напрямую к нативному Security framework macOS. Если
вдруг запускаете это демо на macOS без установленного `truststore`,
переключите источник доверия на «Fetch from API» или «CA file» — без него
источник «OS trust store» молча откатится к контексту, который не видит CA,
установленный только в Keychain.

## 📊 Вердикты

Каждая цель даёт по одной строке на линию и один вердикт на пару.

![Завершённый прогон: строка счётчиков показывает PASS 2, FAIL 0, VOID 1, ERROR 0; три карточки результатов для example.com, example.org и example.net показывают PASS, PASS и VOID, у каждой — строки базовой линии и линии BlankTrail и свёрнутый необработанный дамп по каждой линии.](assets/screenshots/results.png)

| Вердикт | Что это значит |
|---|---|
| `PASS` | Базовая линия была заблокирована (или отключена), и линия BlankTrail прошла. |
| `FAIL` | Базовая линия была заблокирована (или отключена), и линия BlankTrail **тоже** не прошла. Это одна точка данных о том, что BlankTrail не прошёл в этом прогоне, — а не утверждение, что в BlankTrail есть дефект. |
| `VOID` | Прогон ничего не доказал: либо базовая линия тоже прошла беспрепятственно — это возможно, только когда она запущена, и значит, что в этот момент цель не защищалась активно, — либо одна из запущенных линий вернула ответ, который классификатор не смог прочитать ни как блокировку, ни как чистую страницу; откройте её необработанный дамп и прочитайте сами. VOID — это не дефект. |
| `ERROR` | Сам запрос не удался — сеть или TLS — раньше, чем вообще можно было бы дойти до вердикта о блокировке. |

Когда базовая линия отключена (`off`), `PASS` означает только то, что
BlankTrail прошёл; сам по себе он не доказывает, что цель вообще защищается
от голых клиентов (см. «Две линии» выше).

## ❤️ О BlankTrail

Демо свободно и открыто, чтобы его сравнение мог проверить кто угодно, а не
принимать на веру, — каждый вердикт получен из прогона, который вы можете
повторить сами. [BlankTrail Proxy](https://blanktrail.com) — это продукт,
который здесь измеряется; репозиторий существует, чтобы показать его в
работе, а не описать, как он устроен внутри.
