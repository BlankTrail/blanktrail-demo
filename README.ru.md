# BlankTrail Proxy — демо прохождения защиты от ботов

Демо, наглядно и воспроизводимо отвечающее на один вопрос: голый Python-клиент не проходит через сайт, защищённый Cloudflare или AWS WAF, а BlankTrail Proxy — проходит.

## Что демо доказывает, а что нет

Демо запускает две автоматизированные линии против одной и той же цели и сравнивает результат. Ручного эталонного прогона в настоящем Chrome здесь нет, и о цели демо не знает ничего сверх того, что видят эти две линии.

Отсюда два следствия для чтения результатов:

- **`FAIL` означает «через BlankTrail не прошли именно в этом прогоне»**, а не «в BlankTrail есть дефект». У сайта, защищённого от ботов, бывают перебои, A/B-тесты правил и просто развитие защиты со временем; один FAIL — это одна точка данных, а не приговор продукту.
- **`VOID` — это не провал.** Он значит, что прогон вообще ничего не установил: либо базовая линия тоже прошла беспрепятственно (то есть в этот момент цель не защищалась активно), либо одна из двух линий вернула ответ, который классификатор не смог прочитать ни как «заблокировано», ни как «чисто». В обоих случаях ничего не доказано — именно это и говорит VOID, без экивоков.

`PASS` читается симметрично: при работающей базовой линии он означает, что BlankTrail прошёл там, где голый клиент — нет; при отключённой базовой линии (`off`) он означает только то, что BlankTrail прошёл, и сам по себе не доказывает, что цель вообще применяет защиту от ботов (см. «Две линии» ниже).

## Требования

- Python 3.10 или новее.
- Работающий инстанс BlankTrail Proxy — либо один или несколько уже открытых в нём портов, либо доступный REST API. Сам BlankTrail в это демо не входит.
- Свои цели. Демо не поставляется ни с одной и не предлагает их — см. «Ответственное использование» ниже.

## Быстрый старт

```bash
run.bat                     # Windows
./run.sh                    # Linux / macOS
python -m blanktrail_demo   # если venv с зависимостями уже готов
```

`run.bat` и `run.sh` при первом запуске создают локальный `.venv`, ставят в него зависимости из `requirements.txt` и запускают демо. Чтобы сделать то же самое руками:

```bash
python -m venv .venv
source .venv/bin/activate      # на Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m blanktrail_demo
```

В любом случае процесс печатает адрес и открывает его в браузере:

```
BlankTrail demo -> http://127.0.0.1:8790/
```

Веб-интерфейс слушает только `127.0.0.1` — доступен с этой машины, но не из сети, — и не имеет собственной авторизации; меняйте `--host` только если понимаете, что именно открываете наружу. Полезные флаги:

| Флаг | По умолчанию | Значение |
|---|---|---|
| `--port N` | `8790` | порт веб-интерфейса |
| `--host ADDR` | `127.0.0.1` | адрес, на котором слушает веб-интерфейс |
| `--no-open` | выкл. | не открывать окно браузера автоматически |

На самой странице: вставьте цели в поле **Targets**, по одному URL на строку (`#` начинает комментарий; пустые строки игнорируются; до 200 целей за прогон), выберите режимы обеих линий ниже и нажмите **Run**. Результаты приходят потоком в реальном времени — с бейджем вердикта и разворачиваемым необработанным дампом по каждой линии.

## Две линии

Каждая цель запрашивается дважды: один раз **базовой линией** (голый клиент `requests`/`httpx`, без какого-либо участия BlankTrail) и один раз **линией BlankTrail** (тот же клиент, но через порт BlankTrail). У базовой линии три режима:

| Режим | Что происходит | Когда использовать |
|---|---|---|
| `upstream` (по умолчанию) | Запрос базовой линии идёт через вышестоящий прокси, который вы указываете | Когда сравнение ниже должно реально что-то значить (рекомендуется) |
| `direct` | Запрос базовой линии уходит напрямую с этой машины | Для быстрой проверки «на дым» — см. предупреждение ниже |
| `off` | Базовая линия вообще не запускается | Когда вы уже знаете, что цель проверяет голых клиентов, и хотите проверить только BlankTrail |

**Направьте базовую линию через тот же вышестоящий прокси, что и порт BlankTrail.** Линии сравнимы, только если обе выходят с одного и того же исходящего IP-адреса — тогда единственная разница между ними — TLS/HTTP2-отпечаток и solver, а это и есть предмет измерения. Запустите базовую линию в режиме `direct` — и это перестаёт быть правдой: она выходит с другого IP, чем линия BlankTrail, и тогда PASS или FAIL может на самом деле объясняться репутацией именно этого IP, а не тем, что сделал BlankTrail. Демо не скрывает это — режимы `direct` и `off` оба выводят предупреждение в шапке прогона именно по этой причине.

## Два способа подключиться к BlankTrail: готовый прокси-порт или REST API

Линии BlankTrail нужен URL прокси для каждой цели. Демо получает его одним из двух способов.

**Готовый прокси-порт** — один или несколько портов, уже открытых вами в BlankTrail, вставленные как есть:

```
http://127.0.0.1:9000
http://127.0.0.1:9001
```

Одна строка — это фиксированный порт, используемый для всех целей; несколько строк — это пул, который перебирается по кругу (round-robin) по индексу цели. Демо только читает эти порты и никогда само их не открывает и не закрывает — ими управляете вы.

**REST API** — демо открывает один порт на весь прогон и закрывает его по завершении:

```
API base URL: http://127.0.0.1:8891
Порт: 9000        Протокол: HTTP CONNECT
```

По порядку:

1. `GET /api/v1/health` — проверяется заранее, до первого запроса к цели, чтобы неверный базовый URL API или ключ провалился один раз и сразу, а не по разу на каждую цель.
2. `POST /api/v1/ports/open` — открывает порт с настройками из формы (протокол, режим профиля, фильтры браузера/ОС, вышестоящий прокси и переключатели, включая **Challenge Breaker (`js_solver`)**, спуфинг HTTP/2, авто-ротацию профиля и сохранение сессий).
3. Каждая цель после этого запрашивается через `http://127.0.0.1:<порт>` (или `socks5h://127.0.0.1:<порт>` для порта SOCKS5).
4. `POST /api/v1/ports/close` — закрывает порт в конце прогона, если не снята галочка **Close the port when done**. Закрытие не гарантировано: если оно не удастся, это никак не повлияет на уже полученные вердикты.

Введённый вами API-ключ отправляется только на настроенный вами базовый URL API, в заголовке `X-API-Key`, и хранится только в памяти на время прогона — никогда не записывается на диск и не попадает ни в один лог или событие.

## Вердикты

| Вердикт | Что это значит |
|---|---|
| `PASS` | Базовая линия была заблокирована (или отключена) и линия BlankTrail прошла. |
| `FAIL` | Базовая линия была заблокирована, и линия BlankTrail **тоже** не прошла. Это значит, что BlankTrail не прошёл именно в этом прогоне — а не то, что в BlankTrail есть дефект. |
| `VOID` | Прогон ничего не установил: либо базовая линия тоже прошла беспрепятственно (цель в этот момент не защищалась активно), либо одна из линий вернула ответ, который классификатор не смог прочитать ни как блокировку, ни как чистую страницу (откройте необработанный дамп и прочитайте его сами). **VOID — это не дефект**: это значит, что сам тест ничего не доказал, ни в одну, ни в другую сторону. |
| `ERROR` | Сам запрос не удался — сеть, TLS или нечитаемый ответ — раньше, чем вообще можно было бы дойти до вердикта о блокировке. |

Когда базовая линия отключена (`off`), `PASS` означает только то, что BlankTrail прошёл; сам по себе он не доказывает, что цель вообще защищается от голых клиентов (см. «Две линии»).

## TLS и MITM-сертификат

Проверка сертификата на линии BlankTrail **включена по умолчанию**, и это часть измерения, а не формальность: успешное TLS-рукопожатие доказывает, что цепочка подменённого сертификата выстроена корректно, а его SAN совпадает с запрошенным хостом. PASS, полученный при отключённой проверке, на самом деле этого бы не доказывал. (Базовая линия никогда не идёт через прокси BlankTrail, так что всё это её не касается — она всегда проверяет сертификаты как обычный HTTPS-клиент.)

**Ловушка, ради которой всё это написано:** собственный модуль `ssl` в Python прекрасно читает хранилище доверенных сертификатов операционной системы — но `requests` и `httpx` сами по себе им не пользуются. По умолчанию оба при построении SSL-контекста передают `cafile=certifi.where()` — путь к бандлу, который `certifi` носит внутри себя, а не к корням вашей ОС. Поэтому установка CA BlankTrail в систему ничего не меняет для обычного вызова `requests.get()` или `httpx.get()`: доверенный ОС корень лежит рядом, но ни один из клиентов туда не смотрит. Единственное решение — самим построить SSL-контекст и явно передать его клиенту; именно это демо и делает для линии BlankTrail.

Три источника доверия, переключаемые радиокнопкой в блоке **Transport and TLS**:

| Источник | Как строится контекст | Когда нужен |
|---|---|---|
| **OS trust store** (по умолчанию) | `truststore`, если он установлен (читает хранилище ОС через нативный API), иначе собственный `ssl.create_default_context()` из Python | CA BlankTrail уже установлен в систему — обычный случай |
| **Fetch CA from the API** | `GET /api/v1/ca`, объединяется с собственным бандлом `certifi` в один файл на время прогона | Установить CA неудобно или невозможно: контейнер, CI, ноутбук без прав администратора, удалённый инстанс |
| **CA file** | Локальный файл `ca.crt`, который вы указываете, объединяется с бандлом `certifi` тем же способом | CA уже есть в виде файла, и устанавливать его в систему не хочется |

Два последних источника строят **объединённый** бандл — корни `certifi` плюс CA BlankTrail, — а не замену. Цель, исключённая из MITM-порта, предъявляет собственный настоящий сертификат, и бандл, содержащий только корень BlankTrail, не смог бы её проверить. Если выбранный источник не срабатывает (файл не найден, запрос к API не удался), прогон отказывается стартовать — вместо того чтобы молча откатиться к отсутствию проверки: зелёный вердикт не должен получаться на прогоне, где проверять было нечем. Отдельная галочка **Disable TLS verification** существует для диагностики, по умолчанию она снята, и её включение означает, что полученные вердикты больше не доказывают корректность цепочки сертификата.

**Отдельно про macOS.** В Windows и Linux собственный контекст Python из стандартной библиотеки и так читает хранилище ОС, поэтому источник «OS trust store» работает даже без установленного `truststore`. На macOS это не так: CPython сам по себе не читает Keychain, и установленный туда CA для голого `ssl.create_default_context()` попросту невидим. Пакет `truststore` (указан в `requirements.txt` и ставится автоматически скриптами запуска) закрывает этот пробел, обращаясь напрямую к нативному Security framework macOS. Если вдруг запускаете это демо на macOS без установленного `truststore`, переключите источник доверия на «Fetch from API» или «CA file» — без него источник «OS trust store» молча откатится к контексту, который не видит CA, установленный только в Keychain.

## Ответственное использование

Список целей формируете вы сами. Демо не поставляется ни с одной целью и не предлагает ни одной. Тестируйте только те сайты и системы, которыми вы владеете или на тестирование которых у вас есть явное разрешение. Автоматические запросы к инфраструктуре, на тестирование которой у вас нет разрешения, могут нарушать условия её использования и, в зависимости от вашей юрисдикции, закон — и ответственность за это лежит на вас, а не на этом инструменте.
